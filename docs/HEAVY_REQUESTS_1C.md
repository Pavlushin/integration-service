# Обработка тяжелых запросов от 1С

# Текущая схема

```text
1С
 ↓
HTTP запрос
 ↓
Сервис начинает собирать данные
 ↓
20 минут ожидания
 ↓
Возвращается большой JSON
```

Проблемы:

- таймауты;
- повторные запросы;
- высокая нагрузка;
- отсутствие контроля выполнения;
- риск получения дублей.

---

# Новая схема

## Общий поток

```text
1С
 ↓
POST request
 ↓
onec-integration
 ↓
Создание Job
 ↓
RabbitMQ
 ↓
Prepare Worker
 ↓
Сбор данных
 ↓
Создание Send Job
 ↓
RabbitMQ
 ↓
Send Worker
 ↓
POST результата в 1С
```

---

# Что требуется от 1С

Для работы новой схемы необходимо реализовать две интеграционные точки.

## 1. Запрос на формирование отчета

1С отправляет запрос на запуск подготовки данных.

Пример:

```http
POST /onec-api/reports/monthly/request
```

Тело запроса:

```json
{
  "date_from": "2026-06-01",
  "date_to": "2026-06-30",
  "areas": ["all"]
}
```

Ответ:

```json
{
  "accepted": true,
  "job_id": "uuid"
}
```

После получения ответа 1С больше ничего не ожидает.

---

## 2. Прием результата

После завершения подготовки данных сервис самостоятельно отправляет результат в 1С.

Пример:

```http
POST /api/report-result
```

Тело запроса:

```json
{
  "job_id": "uuid",
  "status": "done",
  "data": []
}
```

Таким образом 1С должна иметь HTTP-обработчик для приема готового результата.

---

# RabbitMQ

Используем отдельные очереди:

```text
integration.prepare
integration.send
integration.retry
integration.dlq
```

Назначение:

- integration.prepare — подготовка данных;
- integration.send — отправка результата;
- integration.retry — повторные попытки;
- integration.dlq — окончательно неуспешные сообщения.

---

# Таблица задач

```text
integration_jobs
```

Поля:

```text
id
parent_id

direction
type
status

payload_json
result_json

attempts
last_error

created_at
started_at
finished_at
```

Статусы:

```text
pending
processing
retrying
done
failed
```

---

# Защита от дублей

Для каждой задачи формируется:

```text
dedupe_key
```

Пример:

```text
monthly_report:2026-06-01:2026-06-30:all
```

Если активная задача с таким ключом уже существует:

```text
pending
processing
retrying
```

новая задача не создается.

Возвращается существующая job.

---

# Обработка ошибок

Повторяем выполнение при:

```text
500
502
503
504
timeout
connection refused
```

Пример стратегии:

```text
30 секунд
2 минуты
10 минут
30 минут
```

После превышения лимита попыток:

```text
failed
```

или перенос в:

```text
DLQ
```

---

# Защита от перегрузки

- Авторизация запросов.
- Rate limit.
- Ограничение количества активных задач.
- Ограничение периода формирования отчета.
- Dedupe по параметрам запроса.

---

# Преимущества

- Нет HTTP-запросов длительностью 20+ минут.
- Нет необходимости опрашивать статус задачи.
- Простая логика на стороне 1С.
- Возможность повторной отправки результата.
- Контроль ошибок и повторов.
- Масштабируемая архитектура.
